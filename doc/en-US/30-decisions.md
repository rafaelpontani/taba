| D143 | The segment name is `messages/<topic>/<topicId>/<firstId>_<writer>_<seq>.seg`: **without the ring block** in the path (blocks change with the members, and a stable name cannot depend on them); the `<writer>` and the `<seq>` avoid collision between primaries. The `topicId` prevents a recreated topic from resurrecting messages of the old one. | [33-s3-backup.md](33-s3-backup.md) |
| D144 | The mutable state (delivery, invisibility, dead-letter, deduplication) goes in a **journal** (`.jrn`) every `backup.meta.interval` (60 s), only the **last state**; an ack is a **removal** (a loose message is never deleted); the primary deletes a segment only when **all** its messages have died (no compaction). A message that dies **during the upload** of its segment enters the journal as a removal. Restore is "segments + journals, from oldest to newest". | [33-s3-backup.md](33-s3-backup.md) |
| D145 | The **manager** of a definition (topic or **token**) is its owner on the ring (D123), and it is the one that writes `topics/<name>.json` and `tokens/<id>.json` (the plan said "whoever receives and coordinates" for the tokens; the owner is the only one that all nodes know how to compute). A change is **never refused** because of an S3 failure: it enters a retry queue, and a periodic reconciliation compares with the bucket. | [33-s3-backup.md](33-s3-backup.md) |
| D146 | **Heartbeat and death without a synchronized clock:** each node rewrites `nodes/<id>.json` (id, ips, port, state, increasing `seq`) and whoever observes keeps the ETag and the monotonic instant of the last change; stopped for `backup.dead-after` (60 s) = dead **to whoever observes**; a file seen for the first time counts as fresh until the deadline is completed; unreadable S3 = **unknown** (the behavior without the backup applies). **Alive is not reachable:** the exclusion vote only opens after the candidate's heartbeat expires, and the voters do not recompare (half a heartbeat of difference between observers is accepted). | [33-s3-backup.md](33-s3-backup.md), [07-cluster.md](07-cluster.md) |
| D147 | **The single survivor restores:** the node that starts and finds no one **beating** (only a `member` counts; a `joining` node proves nothing) and **takes the lock** `restore/lock.json` (conditional write; validity `backup.restore.lock-ttl`, renewed by the holder) starts a one-node cluster and restores; without a trace of a cluster only `first-node` or the stop list authorizes. A **running** survivor excludes the dead by itself (even below `cluster.vote.min-voters`) when all the others are dead to the bucket; on seeing members leave, the survivors fetch from S3 what no live node has (also before declaring a loss). On an S3 without conditional write the lock is not safe: warning in the log and accepted risk. Identity: the node that returns is a **new node**. | [33-s3-backup.md](33-s3-backup.md), [07-cluster.md](07-cluster.md) |
| D148 | **Full disk:** above `backup.disk.evict-above` (85%) the node deletes the `.body` of messages already saved, down to `backup.disk.evict-to` (70%); the row stays (the "file first, row after" order holds); reading the absent body does a `Range` on the segment. On flush and drain, at `backup.disk.pause-at` (90%) the move from memory to disk pauses up to `backup.drain.timeout`. | [33-s3-backup.md](33-s3-backup.md), [08-storage.md](08-storage.md) |
| D149 | **Shutdown:** drain sends to S3 everything on disk, the `outbox`, the journal and the definitions **before** the node leaves the cluster (after leaving it stops being the owner of what it would send), within `backup.drain.timeout` (30 s) and without blocking forever; it removes its own heartbeat on finishing. The `stop_grace_period` goes from 40 s to **70 s** in Compose (`drain.timeout` + `backup.drain.timeout` + margin). | [33-s3-backup.md](33-s3-backup.md), [23-operations.md](23-operations.md) |
| D150 | **Operation:** `GET /node/backup`, `POST /node/backup/flush`, `POST /cluster/backup/flush` and `POST /cluster/stop` live in the **operations API** (no token, `operations.allowed-ips`, rate limit `admin` category, like `/node/drain`); what the nodes say among themselves uses `/cluster/backup/flush`, `stop` and `saved` on the cluster port. The flush is three steps and does **not deregister** the node; `/cluster/stop` does the drain on all, and the coordinator (the last) writes `cluster/stop.json` with the nodes and the order. "Start" is starting the processes. Without S3, the two flushes answer `422 backup.not-configured`. | [17-operations-api.md](17-operations-api.md), [18-cluster-api.md](18-cluster-api.md) |
| D151 | The S3 client is the official `aws-sdk-s3` (talks to AWS and MinIO), with short deadlines (connection 3 s, attempt 15 s, operation 30 s, 2 attempts) and **without optional checksums** (`WhenRequired`) to be compatible with older S3s. Optional credentials: without them, the default AWS chain. Building with `aws-lc-rs` worked on Windows (MSVC) without extra tools. | [33-s3-backup.md](33-s3-backup.md), [05-dependencies.md](05-dependencies.md) |

## TUI plan: server work (D152 to D155)

Decided with the plan of the interactive interface ([34-tui-plan.md](34-tui-plan.md), decisions D-TUI-2, 3, 4 and 9) and implemented in `taba-node`. **Written by hand here** (see K in [31-pending-items.md](31-pending-items.md)).

| Code | Decision | Where |
|---|---|---|
| D152 | **Prune is a server operation.** `DELETE /topics/{topic}/messages` (permission `manage` on the topic) empties a queue in the **whole cluster**: the node that receives it asks every member (`POST /cluster/topics/{topic}/prune`, with a `pruneId` that makes it idempotent), prunes itself without the network, waits for all and answers success only if all succeeded; otherwise `503 cluster.prune-incomplete` naming the nodes. No retry or rollback (a rare act; repeating is safe). `removed` counts the messages each node **owned**, so each counts once. | [16-client-api.md](16-client-api.md), [18-cluster-api.md](18-cluster-api.md) |
| D153 | **The operations of one node and of the cluster are in the client API, for the `admin` permission** (D157; the `manage` permission is per topic): `GET /cluster/status`, `GET /cluster/backup`, `/nodes/{nodeId}/metrics`, `/drain` (`GET`, `POST`, `DELETE`), `/backup`, `/backup/flush`, and `POST /cluster/backup/flush` and `/cluster/stop`. The operations API stays as it is, with no token (D63). The cluster-wide routes only mount when the operations API has its own port, because the same names already exist, without a token, on the client port otherwise. | [16-client-api.md](16-client-api.md), [17-operations-api.md](17-operations-api.md) |
| D154 | **The node rule, the same as for a message:** the node that receives `/nodes/{nodeId}/…` compares the `nodeId` with its own; if it is that node it answers from its own data, otherwise it calls the node that has the data **once**, on the cluster port (`/cluster/node-call/{path}`: a call of the operations API that the receiver runs against itself, accepted from members, working even in drain), and never forwards a forwarded call. Unknown `nodeId`: `404 node.not-found`; a node that does not answer: `502 forward.bad-gateway` (or `504`) naming it, with no retry. The existing `/cluster/forward/{path}` was **not** reused: it needs the target to be active and validates the token again, and a node in drain must still be reachable to be returned. | [16-client-api.md](16-client-api.md), [18-cluster-api.md](18-cluster-api.md) |
| D155 | **What any valid token sees, and what a denial says.** `GET /auth/me`, `GET /nodes` (no addresses) and `/stats/topics…` (filtered by the token's prefixes, `403 auth.out-of-scope` outside them) need no special permission; the cluster detail and the inside of the nodes need the `admin` permission (D157). A `403 auth.forbidden` carries `required` (`root` or the permission's name) so a client can say what the token needs. The statistics are the **cluster's** (D156). | [16-client-api.md](16-client-api.md), [19-errors-and-limits.md](19-errors-and-limits.md) |
| D156 | **Consolidated reads.** What each node sees goes on the cluster API (`GET /cluster/stats/topics`, `…/groups`, `GET /cluster/backup/status`, `GET /cluster/status`); the client API (`GET /stats/topics…`, `/cluster/backup`, `/cluster/status`, `/nodes`) asks every member at once under a fixed 5 s deadline and joins them. A node that does not answer does **not** fail a read: `200` with `partial: true` and `missingNodes: [{ nodeId, reason }]` (`timeout`, `unreachable` or `error`); a **write** that fails on a node stays a `503` naming it (the prune). The topic statistics add the counts and rates, take the oldest message, the **maximum** of the latency percentiles and of the groups followed (lower bounds), and evaluate the conditions again on the joined numbers. The operations API's `/metrics/topics*` stay the view of one node. `/nodes/{nodeId}/stats/…` was dropped. | [16-client-api.md](16-client-api.md), [18-cluster-api.md](18-cluster-api.md) |
| D157 | **Two administrators: `manage` and `admin`.** The permission that was called `admin` (change and delete topics, empty a queue, always inside the token's prefixes) is now **`manage`**, and includes `create`. The new **`admin`** is the general administrator: it manages the tokens (`/tokens`) and operates the cluster and the nodes (`/cluster/*`, `/nodes/{nodeId}/…`: status, drain, backup, metrics), reaches every topic (a token with `admin` takes **no** `topicPrefixes`), includes `manage` and `create`, and does not publish or consume. Only the **root token** stops the cluster (`POST /cluster/stop`) and creates, changes or revokes an `admin` token, so an `admin` cannot raise others to its level or remove its peers. **Migration:** the node renames `admin` to `manage` when it opens a `_node.db` of schema 4 (schema 5), and a token that arrives between nodes or from a backup **without** `permissionsSchema` (the version of the permission names, 2 today) reads its `admin` as `manage`: no token gains the new `admin` by the rename. The operations API (no token) is unchanged. | [14-security.md](14-security.md), [16-client-api.md](16-client-api.md), [19-errors-and-limits.md](19-errors-and-limits.md) |
| D158 | **`manage` and `admin` also publish and consume.** The root token, `admin` and `manage` accumulate the roles of `publish` and `consume` (besides `create`): a manager can read, acknowledge and publish messages without a second token. `manage` still respects the `topicPrefixes`; `admin` still takes none. This replaces the clause of D157 that said `admin` does not publish or consume. | [14-security.md](14-security.md) |
