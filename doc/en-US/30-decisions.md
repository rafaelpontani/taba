# Decisions

> **How to read.** The main documentation describes **the result**; here is **the why** (in the format of a decision record, ADR). Each row has the **question code** (to cite: "D13"), the **decision** and **where it is described** in the documents of this folder. The codes are **never reused**. A **provisional** decision is one that the implementation took and that still awaits confirmation: it stays here **and** the question stays in [31-pending-items.md](31-pending-items.md).
>
> **Maintained by hand**, in every language folder, in the commit of the change. The section numbers cited in the "Where" column (e.g. "6.2", "12.8") are those of the original design documents and were kept as they are. **Project rule:** when closing a pending item, record the decision in the technical document, the default value in [22-configuration.md](22-configuration.md), the row here, and **delete** the entry from [31-pending-items.md](31-pending-items.md) and the reference in [32-roadmap.md](32-roadmap.md).

| D125 | The node that synchronizes reads the source's **tombstones** (`GET /cluster/definitions/tombstones`), besides the topic and token streams, to know the versions already used by removed definitions. | D54 | The FIFO queue is the `fifo: true` attribute of a queue, immutable, combinable with volatile and with dead-letter. Discarded alternatives: the whole queue in a single block and the per-group sequencer with data spread by ID. | [09-topics.md](09-topics.md) 16.2 and 16.13 |

| D57 | `groupId` is required on FIFO (`400` without it); a copy of a distributor without `groupId` to a FIFO queue fails only for that queue. | [09-topics.md](09-topics.md) 16.2 and 16.8, [09-topics.md](09-topics.md) 14.2 |
| D58 | One group, one message in flight: the ready list has one entry per free group, the oldest head wins (no fair delivery by bands) and the `GET` batch brings different groups. | [09-topics.md](09-topics.md) 16.6, [12-delivery.md](12-delivery.md) 12.6 and 12.11 |

| D145 | The **manager** of a definition (topic or **token**) is its owner on the ring (D123), and it is the one that writes `topics/<name>.json` and `tokens/<id>.json` (the plan said "whoever receives and coordinates" for the tokens; the owner is the only one that all nodes know how to compute). | D147 | **The single survivor restores:** the node that starts and finds no one **beating** (only a `member` counts; a `joining` node proves nothing) and **takes the lock** `restore/lock.json` (conditional write; validity `backup.restore.lock-ttl`, renewed by the holder) starts a one-node cluster and restores; without a trace of a cluster only `first-node` or the stop list authorizes. | D176 | **The resume works through lives in quarantine and a new ID; the alternatives were dropped.** The node is still born with a new ID, and the disk of each life becomes a folder restored by the new primary, with a check against the dead. Dropped: (1) the `first-node` resuming alone from disk, as development mode did (the other nodes discard their disk and lose what only they had; a network error at the `first-node` with live peers would make it come up alone with old data and split the cluster; it needs a coordinated cold start, D172); (2) a single cluster configuration version (it does not detect what the `ack` changed: a node that was away for a week has the same version and still keeps messages already consumed); (3) "the node with the highest version wins" for messages (they are partitioned by the ring, so the highest-version node does not have everything; the right thing is the union of what each node has, checked against the logs of the dead); (4) releasing each block by witnesses, the old owners that announce the manifest (it forces computing who the old owners were with the factor, the quorum and the ring of the previous life, and proving which table is the final one); (5) a **stable ID between lives**, which would resynchronize only the delta but brings back the out-of-date node that reappears (it stays in [32-roadmap.md](32-roadmap.md)). Out of scope: writing to disk at commit, which would also preserve what was only in memory | [07-cluster.md](07-cluster.md), section 10.1 |

## Ports and the authentication of metrics (D177)

| Code | Decision | Where |
|---|---|---|
| D177 | **The operations port is mandatory and metrics have two doors; `taba-cli` only uses the client port.** `operations.port` has a default (**9090**) and the node always opens the three ports, which must differ. The operations routes (`/health/*`, `/metrics`, `/metrics/topics*`, `/node/drain`, the S3 backup and the restoration) live **only** there, with no token: the network and `operations.allowed-ips` protect them, and their audience is the collectors and the orchestrator inside the infrastructure (Prometheus, Telegraf, probes). The client port serves `/health/live` and `/health/ready` **without a token** (the probes of an orchestrator cannot send one) and `/metrics` with **any valid token** (no particular permission), outside the drain refusal because it describes the node that answers; the rest keeps its rules (`/stats/topics*` for any token, `/nodes/{nodeId}/…` and the cluster for `admin`). `taba-cli` lives outside the infrastructure and **never calls the operations port**: the `health` commands, the `ops-url` profile field and `--ops-url` ceased to exist (a `config.yml` that still has `ops-url` keeps loading, and the field is dropped on the next save), and `cluster status`, `node list`, `metrics [--node <id>]`, `stats …` and `drain … --node <id>` use the client API. **Breaking** (`feat!:`): a node without `operations.port` used to serve the operations routes, with no token, on the client port; a scraper that read `/metrics` there must point to port 9090 or send a token. | [04-architecture.md](04-architecture.md), [14-security.md](14-security.md), [16-client-api.md](16-client-api.md), [17-operations-api.md](17-operations-api.md), [20-cli.md](20-cli.md), [22-configuration.md](22-configuration.md) |

## The OpenAPI contract (D178)

| Code | Decision | Where |
|---|---|---|
| D178 | **Two published OpenAPI 3.1 documents, generated from the routes and served by every node.** The **client** document (`api.port`) and the **monitoring** document (`operations.port`) are built with `utoipa` and `utoipa-axum`: each handler is annotated with its path and registered together with it (`OpenApiRouter`), so a route and its description cannot drift apart. | D180 | **The delivery limit is checked when the message is chosen, and an ack the quorum decided always reaches the owner.** Two bugs found by the chaos run ([37-guarantees.md](37-guarantees.md)). | D179 | **`clippy::significant_drop_in_scrutinee` is on for the whole workspace** (`[workspace.lints.clippy]` in `Cargo.toml`, inherited by `taba-node`), and CI turns the warning into an error (`cargo clippy --all-targets -- -D warnings`). It does not find a guard bound with `let` that is held across a call, nor a lock-order inversion: those stay with the review and with [24-conventions.md](24-conventions.md). | [24-conventions.md](24-conventions.md), [36-known-issues.md](36-known-issues.md) |
